# Deploying MAYOQ AI

Three pieces: **MongoDB Atlas** (data), **Render** (the Express API), **Vercel** (the Next.js
web app). Nothing in this file is a secret — every credential is entered in a hosting
dashboard, never committed.

> The API and the web app each need the other's URL, so the order below matters. Render goes
> up first with a placeholder, Vercel second, then you come back and correct Render.

---

## 1. MongoDB Atlas

In the Atlas console:

1. **Database Access** → confirm a database user exists and you know its password. Click
   *Edit* → *Edit Password* → *Autogenerate* if you are not certain; a password you cannot
   verify is the single most common cause of a failed first deploy.
   Give it the **Read and write to any database** role.
2. **Network Access** → add an allow-list entry. Render's free tier has no static outbound
   IP, so `0.0.0.0/0` is the pragmatic choice. Treat that as a demo-grade setting: it means
   the only thing protecting the data is the password, so the password must be strong and
   must not be one that has ever been pasted into a chat, an issue or a commit.
3. Build the connection string:

   ```
   mongodb+srv://<user>:<password>@<cluster>.mongodb.net/twinrx?retryWrites=true&w=majority
   ```

   **The `/twinrx` before the `?` is required.** Without a database name Mongo connects to a
   default database instead, every query succeeds against nothing, and the app looks empty
   while reporting a healthy connection. If the password contains `@ : / ? # [ ] %`, it has
   to be percent-encoded.

4. Verify the string works *before* deploying anything:

   ```bash
   node -e "require('mongoose').connect(process.argv[1],{serverSelectionTimeoutMS:15000}).then(m=>{console.log('ok:',m.connection.name);process.exit(0)}).catch(e=>{console.log('FAILED:',e.message);process.exit(1)})" "<your connection string>"
   ```

   Run it from `apps/api` so `mongoose` resolves. `bad auth : authentication failed` means
   the user or password is wrong — fix it here, not on Render.

## 2. Render — the API

The repo has a `render.yaml` blueprint, so Render configures itself.

1. Render → **New** → **Blueprint** → pick this GitHub repo. It reads `render.yaml` and
   proposes one service, `mayoq-api`.
2. Render prompts for the values marked `sync: false`:

   | Variable | Value |
   |---|---|
   | `MONGODB_URI` | the Atlas string from step 1, ending in `/twinrx` |
   | `WEB_URL` | `http://localhost:3000` for now — corrected in step 4 |
   | `GEMINI_API_KEY` | your Google AI Studio key |

   `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` and `BILLING_WEBHOOK_SECRET` are generated by
   Render automatically. Do not paste your local development secrets into production.
3. Deploy, then confirm it is alive:

   ```bash
   curl https://mayoq-api.onrender.com/health
   ```

   Expect `{"status":"ok","timestamp":"…"}`. Note the real hostname Render assigns you — the
   rest of this guide calls it `<API_HOST>`.

**Free tier:** the service sleeps after ~15 minutes idle and the next request pays a ~50
second cold start. Before a live demo, hit `/health` once to wake it.

---

## 3. Vercel — the web app

1. Vercel → **Add New** → **Project** → import the repo.
2. **Root Directory: `apps/web`.** This is the one setting that matters and the one that is
   easy to miss; the repo is an npm workspace and a root-level import will build the wrong
   package.
3. Framework preset: **Next.js** (detected automatically).
4. Add one environment variable, for **all** environments:

   | Variable | Value |
   |---|---|
   | `NEXT_PUBLIC_API_URL` | `https://<API_HOST>/api/v1` |

   The `/api/v1` suffix is part of the value. `NEXT_PUBLIC_*` variables are **inlined at
   build time**, not read at runtime — changing this later requires a redeploy, not just a
   restart.
5. Deploy, and note the production domain (`<WEB_HOST>`).

---

## 4. Close the loop

Back in Render → `mayoq-api` → **Environment**, set:

```
WEB_URL = https://<WEB_HOST>
```

No trailing slash. In production the API rejects any browser origin that is not listed
here, so until this is correct every request from the deployed site fails CORS while
`curl` keeps working — which reads like a frontend bug and is not one.

`WEB_URL` accepts a comma-separated list. To let Vercel preview deployments reach the API,
add them too:

```
WEB_URL = https://<WEB_HOST>,https://mayoq-ai-git-main-<you>.vercel.app
```

Saving the variable restarts the service.

## 5. Seed the demo clinic

The seed runs from your machine against Atlas — there is no need to run it on Render.

```bash
cd apps/api
MONGODB_URI="<your Atlas string>" GEMINI_API_KEY="<your key>" npx tsx src/jobs/seed.ts
```

Add `--reset` to drop an existing demo clinic first. Note that `npm run seed -- --reset`
does **not** work: npm swallows the flag across the workspace indirection, so call `tsx`
directly as above.

The seed asks Gemini to generate the three synthetic patients, so it needs a working
`GEMINI_API_KEY` and takes a couple of minutes. Every patient is fictional.

It prints the demo logins when it finishes. The one-click demo buttons on the sign-in page
hide themselves automatically once `NEXT_PUBLIC_API_URL` points somewhere that is not
localhost, so on the deployed site you sign in with the credentials normally.

## Troubleshooting

| Symptom | Cause |
|---|---|
| `bad auth : authentication failed` | Atlas user/password wrong. Reset it in Database Access. |
| Site loads, every request fails CORS | `WEB_URL` on Render does not exactly match the Vercel origin. Check scheme and trailing slash. |
| Requests go to `localhost:4000` in production | `NEXT_PUBLIC_API_URL` was missing at build time. Set it and **redeploy** — a restart will not do it. |
| Logged in, but all data is empty | Connection string has no `/twinrx` database name. |
| First request after a pause takes ~50s | Render free tier cold start. Expected. |
| AI panels say unavailable, rules still work | Gemini key missing or out of quota. This is the designed behaviour: the rule engine never depends on the model. |
